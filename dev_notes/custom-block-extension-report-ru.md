# Пользовательские блоки: возможности и ограничения

Анализ исходного кода текущего checkout. Это обзор, а не результат запуска приложения или тестов.

## Вывод

Разработчик приложения уже может написать React-расширение со своим типом блока. Обычный блок получает общую оболочку, вложенность и большую часть взаимодействий от редактора. Для блока-контейнера есть публичные компоненты layout и политика перемещения. Но это пока **API для доверенного кода приложения**, а не готовая система установки расширений конечным пользователем: загрузчик пакетов, изоляция и пользовательский интерфейс управления здесь не установлены самим контрактом редактора.

Автору недостаточно написать один React-компонент. Ему нужно выбрать модель данных и регистрации, знать различие текстового и структурного выделения, обозначать интерактивные области и учитывать установленные расширения. Эти требования частично отражены в примерах, но не собраны в проверяемый end-to-end контракт внешнего автора.

## Как это работает сейчас

1. Приложение создаёт core editor и React runtime, передавая `extensions` в `createReactEditor`; demo делает это для каждого editor через `EditorStorage` ([пример](../demo/src/App.tsx)). `ReactEditorExtension` имеет стабильный `id` и синхронный `setup(reactEditor)`; регистрация также доступна через `extensions.install` и возвращает disposer ([тип](../packages/react-rivto-editor/src/managers/extensions/types.ts), [API](../packages/react-rivto-editor/src/managers/extensions/api.ts)).
2. Для одного блока есть `blockExtension({ definition, render, layout, behavior, slashCommand, clipboard })`. Регистрация объединяет определение типа, renderer и дополнительные интеграции; конфликт зарегистрированного типа приводит к ошибке. Slash-команда и clipboard-конвертер необязательны ([контракт](../packages/react-rivto-editor/src/managers/blocks/types.ts), [фабрика](../packages/react-rivto-editor/src/extensions/built-ins/built-ins.ts)). Тип должен быть стабильным: он хранится в документе. `defaultProps` и `propSchema` задают defaults и проверку свойств.
3. Renderer получает `blockId`, читает реактивный snapshot через `useBlockNode` или `useBlockEditing` и меняет данные через операции редактора. Snapshot не является местом записи; в отложенном callback актуальное значение нужно повторно читать из `panel.blocks.getBlockNode`, как в Counter ([пример](../demo/src/blocks/custom-blocks.tsx), [hook](../packages/react-rivto-editor/src/hooks/blocks/use-block.ts)).
4. Page создаёт occurrence и выбирает layout. Если свой layout не указан, `DefaultBlockLayout` размещает `BlockRow`, `BlockContent`, `BlockBody` и `BlockChildren`; renderer отвечает только за собственное содержимое. Так один и тот же renderer может быть использован в обычной странице, вложенном layout и Edgeless card ([реализация](../packages/rivto-page/src/presentation/components/block-layout/block-node.tsx), [default layout](../packages/rivto-page/src/presentation/components/block-layout/default-block-layout.tsx)). Геометрию, выбор цели drop и обход дочерних блоков автор обычного блока заново не реализует.
5. Для собственного размещения дочерних блоков `layout` компонуется из экспортируемых `@chulane/rivto-page` примитивов, в том числе `BlockRow`, `BlockContent`, `BlockBody`, `BlockChildren` и drop targets. Layout должен сохранить ровно одно отображение каждого дочернего блока; направление списка и зоны drop описывают геометрию, а `behavior.canMove` отдельно отвечает за допустимость перемещения. `behavior.isAvailable` сам ограничивает применимость поведения нужным типом. Примеры: [Columns](../packages/react-rivto-editor/src/extensions/containers/columns/columns.tsx), [контракт layout](../packages/rivto-page/src/presentation/components/block-layout/README.md).

## Выделение, клики и ввод

| Случай                                    | Что делает автор сегодня                                                                                                                                      | Что остаётся редактору                                                                                                        |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Текст                                     | `MarkdownContent` либо один editable с `useBlockEditing(blockId).attributes`. Не рендерить сохранённый текст как React children внутрь этого editable.        | Синхронизация текста, composition, восстановление DOM selection и фокуса; другие команды зависят от установленных расширений. |
| Блок без текста                           | `useBlockNode` плюс `useBlockSelectionAnchor` на области, представляющей тело блока.                                                                          | Начало структурного выделения и восстановление фокуса.                                                                        |
| Самостоятельный control                   | `editorControlProps` на кнопке, input или другом control; автор реализует действие и доступность.                                                             | Учитывает границу control при editor-жестах.                                                                                  |
| Кнопка: клик — действие, drag — выделение | Demo Counter ставит на кнопку одновременно `editorControlProps` и `BLOCK_SELECTION_ANCHOR_ATTRIBUTE`, а в `onClick` проверяет `defaultPrevented` и modifiers. | После захваченного жеста подавляет соответствующий click; сам порог и преобразование selection принадлежат общему коду.       |
| Нестандартный текстовый редактор          | Нужно отдельно разобрать владение фокусом, input и native selection; `preventTextEditingAttributes` позволяет ограничить обычное редактирование блока.        | Готовая универсальная интеграция произвольного вложенного редактора из одного компонента не следует из этого API.             |

Реальные маркеры определены в [constants.ts](../packages/react-rivto-editor/src/constants.ts), а разрешение жеста — в [block-pointer-selection.ts](../packages/rivto-page/src/editor/selection/block-pointer-selection.ts). Там всё ещё есть эвристики по HTML-тегам (`button`, `input`, `a` и т. д.) и специальная логика при совпадении control и anchor. Не следует считать, что общий декларативный механизм ролей уже реализован: [block-authoring-contract.md](../packages/react-rivto-editor/docs/block-authoring-contract.md) сам называет себя design document и предлагает, например, отсутствующие там в качестве готового API `controlAttributes` и `selectionActivatorAttributes`. Реальный Counter использует существующие маркеры явно.

Наличие hook или маркера не гарантирует весь редакторный UX: их документация оставляет Enter/Tab, clipboard, slash и структурное выделение соответствующим расширениям. Например, demo отдельно устанавливает `standardPreset`, `pageDragExtension` и `edgelessPreset`. Хост должен определить поддерживаемую комплектацию, а не предполагать, что `blockExtension` включает все функции.

## Что мешает внешнему автору

1. **Нет одного актуального рецепта от установки до результата.** Demo — полезный работающий по коду пример Counter/Slider, но использует CSS приложения, набор preset и не является отдельным проверенным пакетом расширения. Design document содержит предполагаемые имена рядом с реальными. Старый [tutorial по plugins](tutorials/plugins/00-extension-model.md) описывает другой API (`editor.use`, `PluginManager`) и не должен служить текущей инструкцией без сверки.
2. **Контракт интерактивных областей требует знания деталей движка.** Автор сам комбинирует маркеры, учитывает `defaultPrevented` и modifiers. Существуют тесты на отдельные сочетания, но для автора нет явной компактной таблицы обещаний и границ для вложенных control, drag, keyboard и обоих режимов. Нельзя по одному успешному click заключить, что весь UX блока корректен.
3. **Контейнер заметно сложнее leaf-блока.** Публичные примитивы есть, но неверная композиция может нарушить selection, drop geometry, hover, вложенность или отображение детей. Layout и разрешение перемещений — разные обязанности; примитивы сами по себе не доказывают правильность конкретной композиции. Нужен пример внешнего контейнера с пустым и заполненным состояниями и проверкой drop/undo.
4. **Совместимость сохранённого содержимого — обязанность хоста.** При отсутствии renderer есть настраиваемый `unknownBlockRenderer`; он не устанавливается автоматически самим типом опции ([options](../packages/react-rivto-editor/src/editor/types.ts), [fallback](../packages/react-rivto-editor/src/blocks/unknown-block/unknown-block.tsx)). Хосту нужно решить, какие расширения доступны при открытии документа, как выглядят отсутствующие типы и что происходит при изменении схемы. Само наличие fallback не доказывает безопасность всех операций редактирования и сохранения неизвестного блока.
5. **Установка внешнего кода — отдельная задача приложения.** `setup` получает API runtime и renderer исполняется как обычный React-код в приложении. В рассмотренном контракте нет механизма изоляции или разрешений; нельзя обещать безопасный запуск недоверенного кода, установку из каталога или одинаковую доступность расширения на всех клиентах совместного документа.
6. **Перенос между приложениями не бесплатен.** Для структурированного блока можно отдельно зарегистрировать clipboard converter, как у Counter; без проверки форматов не стоит обещать полноценный обмен с другими редакторами. Стили renderer и зависимости пакета тоже обеспечивает автор/хост. Хранение данных и сохранение документа обеспечивает приложение, а не React-компонент расширения.

## Что рекомендую сделать

1. Зафиксировать поддерживаемый минимальный набор расширений хоста и написать актуальное руководство с двумя полноценными примерами: текстовый блок и Counter. Включить импорты, регистрацию, CSS, изменение данных, cleanup, поведение при отсутствии блока и реальные правила control/anchor. Явно отделить текущий API от проектных предложений.
2. Вынести пример в отдельный workspace-пакет, использующий только публичные exports, и подключить его в demo как внешний потребитель. Это проверит не только исходники внутри монорепозитория, но и доступность типов/стилей и реальный путь интеграции. Для текстового и control-блока проверить Page и Edgeless, click против drag, keyboard, undo и сохранение/повторное открытие.
3. Добавить отдельный пример контейнера на общих Page primitives: пустой и заполненный, вложенный, с объявленной геометрией и `canMove`. Проверить реальную цель drop, порядок, отказ недопустимого перемещения и undo в обоих режимах. До этого не объявлять произвольный контейнер простым или автоматически корректным.
4. По результатам примеров уточнить публичный контракт взаимодействий. Предложенные роли из design document — возможное направление, но сначала нужно проверить, где действующие маркеры и эвристики недостаточны; не требуется создавать новую абстракцию только ради переименования.
5. Если цель — именно расширения, устанавливаемые конечным пользователем, отдельно спроектировать распространение, доверие и изоляцию, версии API и схем, доступность на всех клиентах и обработку отсутствующих расширений. Текущая регистрация React-кода является строительным блоком для хоста, а не решением этих задач.

## Границы проверки

Проверены исходные типы и точки регистрации, demo Counter/Slider, Page layout и pointer-selection, а также наличие релевантных browser-тестов ([selection](../e2e/selection.spec.ts), [Edgeless](../e2e/edgeless.spec.ts), [clipboard](../e2e/clipboard-converters.spec.ts)). Тесты и приложение в рамках этого анализа не запускались; наличие тестов не подтверждает их текущий результат или полное покрытие внешних пакетов. Код редактора не изменялся.
