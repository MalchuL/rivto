# Кодовый стиль Rivto

Рабочая редакция для TypeScript и React в пакетах редактора. Основа — [AGENTS.md](../AGENTS.md), [ESLint](../eslint.config.js), [Prettier](../.prettierrc.json) и примеры реализации.

Руководство написано по-русски для удобства чтения. В исходном коде пишите JSDoc и комментарии на английском, в том числе перед `return`. Примеры кода в руководстве следуют тому же правилу.

Пока идёт обсуждение, все согласованные правила записываем только в этот файл. Перенос в `AGENTS.md` обсудим отдельно.

## Как писать код

1. **Давайте переменным и функциям читаемые имена из нескольких смысловых слов.** Имя переменной должно объяснять, какое значение она хранит и какую роль оно играет. Например, `selectedBlockIds` показывает, что это идентификаторы выбранных блоков, а `ids` оставляет оба вопроса открытыми. Имя функции должно объяснять, что она делает или какие данные возвращает. Например, `findBlockById` описывает и результат поиска, и его критерий. Используйте принятую в проекте терминологию. Каждое слово должно уточнять смысл. Для параметра короткого callback допустимо однословное предметное имя, когда его роль ясна из выражения, например `selectedBlocks.map((block) => block.id)`. Команды `moveBefore`, `moveAfter` и `moveInside` явно задают положение блока относительно указанного ID. Для типов и компонентов используйте `PascalCase`, для функций и значений — `camelCase`, для каталогов — `kebab-case`. Имена типов и интерфейсов описывают их назначение. Используйте `MoveBlockOptions` и для `type`, и для `interface`. Префиксы `T` и `I`, обозначающие вид объявления, опускайте. [Команды блока](../packages/react-rivto-editor/src/hooks/blocks/use-block.ts)
2. **Пишите ветвления так, чтобы каждый исход можно было прочитать отдельно.** Для одного простого выбора подходит тернарный оператор. Для нескольких условий используйте ветвления. Ранний `return` допускается при короткой проверке без сложной внутренней логики. Перед каждым таким выходом ставьте комментарий, чтобы при чтении сразу было видно, где функция возвращает управление. Если ветви `if` и `else` завершаются отдельными `return`, пометьте каждый из них, даже когда условие и результат очевидны. Обычный завершающий `return` после всех ветвлений можно оставить без комментария, даже если выше есть ранние выходы. У условий и циклов всегда ставьте фигурные скобки. Содержимое непустого блока начинайте с новой строки, закрывающую скобку ставьте отдельно.

   ```ts
   if (direction === "before") {
     // Return the previous sibling.
     return siblings[index - 1];
   } else {
     // Return the next sibling.
     return siblings[index + 1];
   }
   ```

3. **Ориентируйтесь на 50 строк и предпочитайте простые функции.** ESLint учитывает пустые строки и комментарии и предупреждает о превышении. Сначала поищите самостоятельные операции, которые можно осмысленно назвать и переиспользовать. Если функция решает одну сложную задачу, таких операций выделить не удаётся и последовательность действий легче понять целиком, допустимо оставить больше 50 строк. Приватные методы класса размещайте в конце, включая статические и методы с `#`.
4. **Поручайте механическое форматирование Prettier.** В проекте отступ в два пробела, двойные кавычки, точки с запятой, завершающие запятые и ориентир ширины в 100 символов. В многострочном тернарном выражении `?` и `:` открывают строки. Используйте ES-модули. Внутри исходников React-пакета для локальных модулей используйте относительные импорты.
5. **Документируйте контракт функции.** Перед функцией, методом, хуком, компонентом, конструктором, аксессором и объявленным callback-контрактом пишите многострочный JSDoc. Начните с поведения, затем отдельным абзацем укажите существенные условия. Через `@param` поясните параметры, включая значимые поля деструктурированных props. В `@returns` опишите результат, отсутствие значения или завершённый эффект, в `@throws` — существенные ошибки. Для конструктора и сеттера описание возврата не требуется. Однострочные докстринги функций и методов недопустимы. Пишите полное, читаемое описание и сохраняйте полезные детали существующей документации. Существующий код приводите к стилю отдельным рефакторингом только по запросу. При изменении поведения обновляйте описание затронутого контракта. Комментарий внутри алгоритма должен объяснять причину решения или пограничный случай.

### Единицы измерения и координаты

Если число задаёт длительность, расстояние или ограничение размера, указывайте единицу измерения в имени. Например, `IMAGE_LOADING_DELAY_MS` задаёт задержку в миллисекундах, а `MAX_FILE_NAME_BYTES` — предел в байтах. Когда в одном расчёте участвуют координаты в разных системах отсчёта, отражайте это в именах, например `clientX` и `canvasX`.

### Выбор режима при вызове функции

Если аргумент выбирает режим операции, указывайте значение, смысл которого виден в месте вызова. Например, в `moveBlock(blockId, targetId, "before")` сразу видно, куда переместится блок. Позиционный флаг `true` потребовал бы свериться с объявлением функции. Для обычного признака с двумя состояниями используйте булево значение с понятным именем, например `isReadOnly`.

### Терминология проекта

Перед выбором имени проверьте, как это понятие уже называется в коде и документации проекта. Используйте установленный термин последовательно. Не придумывайте синонимы, сокращения и новые названия для уже известных понятий.

Принятые термины записывайте в `GLOSSARY.md`. Группируйте их по предметным областям, чтобы близкие понятия можно было прочитать рядом. Например, `Selection`, `Block range` и `Resolved selection` относятся к выделению. Для каждого термина указывайте принятое название и краткое определение. [Примеры действующих терминов](../CONTEXT.md#language)

### Параметры функций и props компонентов

Применяйте ориентир «7 ± 2» к каждому уровню отдельно. Например, у функции с аргументами `blockId` и `options` два параметра. Если в `options` десять полей, ищите смысловые группы внутри самого `options`. Когда параметры образуют смысловую группу, объединяйте их в объект с именованным типом аргументов. Если тип аргументов нужен одной или нескольким функциям в одном файле, объявляйте его в этом файле. Если общий тип нужен функциям из разных файлов, объявляйте его в `types.ts`. Когда оба файла относятся к одной фиче, держите `types.ts` в её каталоге. Для типа, общего нескольким фичам, выбирайте расположение по ситуации, учитывая назначение контракта и места его использования. То же правило действует для props компонентов. Например, если `BlockPickerProps` нужен только компоненту `BlockPicker`, объявляйте их рядом.

Если у объекта есть устоявшееся предметное имя, используйте его. Например, ссылка на блок — `BlockReference`. Для остальных случаев выбирайте суффикс по роли:

- `Options` — настройки, влияющие на выполнение операции.
- `Args` — аргументы конкретного вызова, объединённые в объект.
- `Props` — параметры React-компонента.

В `Args` и `Props` помечайте поле как `readonly`, если функция или компонент только читает его. Например, `readonly blockId: string` запрещает переприсвоить `args.blockId` через этот тип. Для поля с объектом модификатор действует на само поле. Для массива допустима запись `readonly blocks: readonly Block[]`. Второй `readonly` запрещает менять состав и порядок элементов через это поле. Его применение остаётся на усмотрение автора.

### Выбор между `interface` и `type`

- Используйте `interface` для контракта, который планируется расширять или реализовывать в классе.
- Используйте `type` для простых данных, аргументов функций и props компонентов, включая props с callback. Например, для `BlockPickerProps` с полями `blockId` и `onSelect` подходит `type`.
- Для объекта, который собирается из `{}` или создаётся объектным литералом с методами, также используйте `type`, если контракт не предполагает расширения или реализации классом. Например, объект операций `BlockOperations` с методами `moveBefore` и `moveAfter` при таких условиях описываем через `type`. Само наличие методов не требует `interface`.
- Если вызывающий код работает с объектом исходного класса или типа, передавайте объект целиком и используйте его тип в сигнатуре. Например, если у вызывающей стороны уже есть `Block`, передавайте `block`, даже когда функция читает только `id` и `documentId`.
- Частичный аргумент оправдан, когда вызывающая сторона действительно работает с другими данными и сама конструирует объект для передачи. Например, новая фича получает `id` и `documentId` и собирает из них ссылку на блок. Если ссылка на блок имеет самостоятельный смысл для фичи, используйте существующий именованный тип `BlockReference` или объявите его. `Pick<Block, "id" | "documentId">` уместен, когда аргумент по смыслу представляет именно часть `Block` и вызывающий код действительно передаёт только эти поля. Само добавление фичи не требует менять существующий контракт.
- Предпочитайте готовые типы и интерфейсы целиком. Используйте `Pick` и `Omit` только при реальной необходимости передавать сокращённую форму, а `&` и `|` — когда сочетание или варианты типов отражают допустимые значения.

## Как устроить изменение

6. **Исправляйте поведение там, где определяется его результат.** CRDT-контракты и адаптер принадлежат `crdt-doc`, правила сохранённого документа и иерархии — `document-model`, команды и выбор — `rivto-editor-core`, DOM, рендеринг и браузерные жесты — `react-rivto-editor`. Нативный импорт `yjs` держите внутри адаптера. Например, React-команда `moveInside` передаёт намерение менеджеру, а изменение структуры хранится в модели. [Хук блока](../packages/react-rivto-editor/src/hooks/blocks/use-block.ts) · [Менеджер блоков модели](../packages/document-model/src/core/managers/block-manager/block-manager.ts)
7. **Различайте владельца и потребителя.** Контроллер хранит одно поле для каждого менеджера. Владелец создаёт объект и отвечает за его освобождение. В типе, который получает потребитель, перечисляйте только нужные ему операции. Тот же экземпляр можно передать через узкий интерфейс без обёртки, дублирующего поля или приведения типа. При изменении API прочитайте весь путь от создания до освобождения. [Жизненный цикл DocumentEditor](../packages/rivto-editor-core/src/editor/document-editor.ts)
8. **Выбирайте объём чтения по тому, что отображает компонент.** Для собственных полей блока и ID прямых детей используйте `useBlockNode`. Когда действительно нужен снимок всего поддерева, используйте `useBlock`. Снимок служит для чтения. Изменения проводите командами через менеджер, связанные записи документа объединяйте в транзакцию. [Подписки и операции блока](../packages/react-rivto-editor/src/hooks/blocks/use-block.ts)
9. **Проверяйте наблюдаемое поведение.** Для правила модели подходит Jest-тест, для фокуса, DOM-выделения и жеста на поверхности — Playwright через пользовательское действие. Когда изменение затрагивает обе поверхности, проверяйте Page и Edgeless. Для функций и исправлений выполняйте принятый в репозитории цикл проверки производительности. [Порядок проверок](../.agents/skills/rivto-performance-testing/SKILL.md)

### Структура папок

1. **Сначала определите, кому принадлежит поведение.** Внутри пакета используйте уже принятые каталоги. Например, операция над блоками в ядре относится к `managers/block-manager/`, а поддержка изображений в React — к `extensions/image/`. Если фича затрагивает несколько слоёв, каждый слой хранит свою часть реализации. [Менеджер блоков](../packages/rivto-editor-core/src/managers/block-manager/block-manager.ts) · [Расширение изображений](../packages/react-rivto-editor/src/extensions/image/image.tsx)
2. **Храните код рядом с тем, что его использует.** Хук изменения размера изображения лежит в `image/view/hooks/`. По пути видно, какой фиче и какой её части он нужен. Если появляются потребители из других фич, выбирайте общий модуль по назначению кода. [Хук изменения размера](../packages/react-rivto-editor/src/extensions/image/view/hooks/use-image-resize.ts)
3. **Создавайте вложенную папку, когда можете назвать отдельную задачу внутри фичи.** В `extensions/file/` каталог `ingestion/` объединяет обработку входных файлов, а `view/` — их отображение. У небольшого модуля реализация может лежать прямо в его каталоге. Набор подпапок определяется содержимым. [Обработка входных файлов](../packages/react-rivto-editor/src/extensions/file/ingestion/file-ingestion.ts) · [Отображение файла](../packages/react-rivto-editor/src/extensions/file/view/file-view.tsx)
4. **Давайте каталогам имена из словаря проекта и пишите их в `kebab-case`.** Для предметной логики выбирайте имя, по которому её можно найти, например `block-transfer/` или `block-resize/`. Каталог `__tests__/` именуйте по принятому соглашению для тестов.
5. **Держите небольшую вспомогательную функцию в файле её потребителя.** Когда у функции появляется самостоятельная задача или она нужна нескольким файлам, вынесите её в модуль с предметным именем, например `image-input.ts`. Располагайте модуль рядом с фичей, которой он принадлежит. Создавать папку `utils/` для каждой фичи необязательно.

### Файлы `index.ts`

В `index.ts` разрешены только реэкспорты из других файлов. Типы, интерфейсы, функции, классы, константы и другие объявления размещайте в соответствующих модулях. Явно перечисляйте имена значений в `export { … } from` и имена типов в `export type { … } from`. Реэкспорт через `export *` запрещён.

```ts
export { DocumentEditor } from "./document-editor";
export type { MoveBlockOptions } from "./types";
```

### Размещение тестов

- Модульные и интеграционные Jest-тесты размещайте в каталоге `__tests__/` соответствующего модуля или пакета. Используйте суффикс `.test.ts` или `.test.tsx`.
- Сквозные Playwright-тесты размещайте в корневом каталоге `e2e/`. Используйте суффикс `.spec.ts`.
