# Динамические JavaScript-расширения в демо

В демо добавлен эксперимент независимой сборки и загрузки четырёх расширений:

- `dynamic.counter`: клик по свободной области выделяет блок, кнопка меняет счётчик, drag от кнопки выделяет блок без лишнего клика;
- `dynamic.accordion`: сворачивает и раскрывает канонических детей и объявляет зону приёма для пустого и заполненного списка;
- `dynamic.note`: collaborative plain-text contenteditable через `useBlockEditing`;
- `dynamic.status`: checkbox со своим pointer-взаимодействием внутри выделяемого блока.

Их исходники — обычные JavaScript-модули в `demo/src/dynamic-extensions/`. Каждый экспортирует `createExtension()`, который создаёт отдельную регистрацию для конкретного runtime. Все четыре типа доступны через slash-команды. Общий CSS примера находится в `styles.css` рядом с исходниками и загружается отдельным файлом.

## Сборка и загрузка

`pnpm --dir demo build:extensions` компилирует каждый модуль в отдельный ESM-файл в `demo/public/dynamic-extensions/`. Обычные `pnpm demo` и `pnpm demo:build` также запускают эту сборку. Команда ниже пересобирает только файлы расширений непосредственно в уже построенное демо:

```sh
pnpm --dir demo build:extensions dist/dynamic-extensions
```

Список URL хранится отдельно в `demo/public/dynamic-extensions.json` и при production-сборке копируется в `demo/dist/dynamic-extensions.json`. Сервер должен отдавать этот список, модули и `dynamic-sdk/`. Приложение получает список через `fetch`, загружает каждый модуль через динамический `import()` и создаёт свежие регистрации для каждого runtime. При создании редакторов они устанавливаются через обычный массив `extensions`; владельцем регистрации и её очистки остаётся `ExtensionManager` редактора.

React-хуки и контексты не работают правильно с отдельной копией React или редактора. Поэтому хост до импорта публикует свои экземпляры React, Page, React editor и Zod, а import map разрешает соответствующие bare imports в небольшие ESM-модули `dynamic-sdk/`. Исходник расширения при этом импортирует обычные имена пакетов. Эти фасады содержат только exports, необходимые четырём примерам; они не являются полноценным стабильным SDK.

## Найденные проблемы и решения

1. **Загрузка через `import.meta.glob` не даёт независимой сборки.** Она создавала chunks, но список модулей входил в bundle приложения. Теперь список загружается по HTTP, а JS компилируется отдельной командой. Playwright подменяет список и проверяет, что состав установленных типов меняется без сборки приложения.
2. **Отдельно собранный React ломает контексты и хуки.** Import map и фасады используют экземпляры библиотек хоста, а не включают их копии в файлы расширений.
3. **Выделение control и действие конкурируют за жест.** Counter использует структурный anchor и `editorControlProps`; button также явно становится anchor и игнорирует `defaultPrevented` и selection modifiers. Это соответствует существующему контракту pointer selection. Клик по пустой части выделяет блок, клик по кнопке изменяет данные, drag не активирует её.
4. **Цвет renderer мог закрыть заливку выделения.** Фон примера использует `--rivto-block-selection-fill`, когда редактор задаёт его. Тест проверяет и состояние, и вычисленный цвет.
5. **Самодельный список дочерних блоков ломает общую геометрию и иерархию.** Accordion компонирует `BlockRow`, `BlockContent`, `BlockBody` и ровно один `BlockChildren`, включая пустую зону приёма. `listProps.collapsed` использует существующий механизм скрытия и reconciliation selection.
6. **Plain-text editable не получал семантическую роль textbox.** Пример задаёт `role="textbox"` и `aria-multiline`; текстом владеет hook, а не React children.
7. **Сбой загрузки давал пустой экран.** Теперь приложение показывает текст ошибки и пишет причину в консоль.

## Текущие границы

- Это демонстрационный загрузчик: он загружает список при запуске, до создания runtime. Смена списка применяется после перезагрузки страницы; UI установки и обновление уже открытых runtime не реализованы.
- Список доступных экспортов в `dynamic-sdk/` поддерживается вручную. Для произвольного блока потребуются дополнительные exports или продуманный публичный SDK. Абсолютные пути рассчитаны на размещение демо в корне origin.
- Четыре примера используют один общий независимо доставляемый CSS-файл. Загрузчик пока не управляет отдельным набором стилей для каждого расширения.
- Вопросы доверия, версий, распространения пакетов и установки намеренно оставлены за рамками эксперимента. Файлы выполняются в том же контексте, что и приложение.
- Сборка демонстрационных JS-файлов проверяет синтаксис, но TypeScript не проверяет их типы: здесь нет контракта типизации внешнего JS-пакета.

## Проверка

Production-сборка и `pnpm demo:check` прошли. `e2e/dynamic-extensions.spec.ts`: 14 проверок на Chromium и Firefox с 12 workers; отдельно связанные сценарии Counter в `e2e/selection.spec.ts`: 24 проверки, оба браузера. Действия включают реальный pointer drop в пустой accordion, undo/redo, сворачивание и раскрытие, выбор блока и работу controls на Page и Edgeless. Сценарий с наполненным accordion и drop между его детьми отдельно не проверялся.

На production preview в headless Chromium выполнены последовательные замеры на обычном demo и `?repeat=200`, по пять прогретых кликов после одного прогревочного. Для сопоставления в том же билде использован встроенный demo Counter; это не baseline до изменения. От pointerdown до обновления текста и двух animation frames медиана динамического Counter составила 30,6 мс (30,6–30,9) и 40,1 мс (34,0–49,7) соответственно; у demo Counter — 29,5 мс (29,4–29,9) и 34,9 мс (33,6–44,4). Отдельный прямой вызов `blocks.setBlockProp` дал медиану 0,3 и 0,5 мс для динамического Counter; он измеряет синхронную команду с подписчиками, но не весь pointer path. Два кадра — лишь приближение времени обновления, а не доказательство завершения всей отложенной верстки. Полный performance-профиль и сравнение со старым билдом не выполнялись.
