# Архитектура React-редактора: решение и выполнение

Этот файл — согласованный план рефакторинга packages/react-rivto-editor.
К нему следует обращаться при продолжении работы и оценке изменений.

## Решение

Выбран вариант «контроллеры поведения + небольшие React-компоненты».
Статическое оформление переносится из TSX в существующие CSS-файлы рядом
с функцией редактора. React остаётся слоем отображения и подключения к DOM.
Переписывать компоненты на React.Component или выделять новый npm-пакет не нужно.

Текущая основа сохраняется: ReactEditorImpl собирает менеджеры,
EditorViewController владеет отображением документа, PageDragController —
перетаскиванием, DocumentViewDOM — поиском внутри одного document view.
Core продолжает владеть документными командами, транзакциями и undo.

## Почему это нужно

Похожие обязанности сейчас оформлены по-разному: классы, длинные hooks,
функции регистрации с изменяемыми замыканиями, функции с несколькими WeakMap.
useBlockEditing совмещает React-подписки, текстовую синхронизацию, IME и фокус.
TODO совмещает определение данных, операции, renderer, диалог и установку.
EdgelessVisualController содержит инструменты, операции и clipboard в одном классе.
Стили распределены между CSS, Tailwind-строками и inline-объектами.

## Правила

- Менеджер владеет общими регистрациями и операциями; контроллер — состоянием
  конкретного поведения. Компонент описывает UI, hook подключает его к React.
- Каждый изменяемый объект имеет одного владельца и явную очистку ресурсов.
- Документные сервисы существуют на документ; DOM и overlays — на отображение;
  IME и текстовая синхронизация — на editable; временные listeners — на жест.
- Создание контроллера во время render не подключает внешние ресурсы.
  Подключение выполняется после commit, cleanup допускает повторный mount.
- Компоненты не дублируют данные документа. Подписки остаются узкими,
  неизменившиеся snapshots сохраняют ссылки. Покадровый preview не обновляет
  всё React-дерево.
- Чистые вычисления могут оставаться функциями. Не нужны BaseExtension,
  универсальный сервисный контейнер и классы, существующие только ради синтаксиса.
- Общими становятся операции с реальными потребителями: DOM-поиск, selection,
  размещение, slots и команды. Расширения регистрируют свои обработчики через
  существующие менеджеры.
- Статические стили — в feature CSS; визуальные состояния — в selectors и
  data-атрибутах; тема — в публичных CSS variables; координаты/zoom — динамические.
  React и контроллер не должны независимо записывать одно свойство геометрии.
- Shadcn primitives остаются независимыми от редактора. Маркеры editor controls
  принадлежат расширениям или общим редакторским controls.
- Короткие английские комментарии объясняют причины и границы ответственности.
  Существующая документация переносится вместе с реализацией.

## Порядок выполнения

1. Block drag: отделить overlay и статические стили от provider;
   сохранить PageDragController владельцем жеста и preview position.
2. Согласование карточек: собрать настройки, memberships и очередь в
   BlockElementProjection с методами schedule/reconcile/destroy.
3. useBlockEditing: выделить контроллер editable с синхронизацией текста,
   composition, фокусом и cleanup. Сохранить публичный hook и его контракт.
4. Text selection и edgeless transform: состояние и обработчики жестов оформить
   как методы контроллеров; функции установки оставить точками подключения.
5. TODO: разделить данные, действия, renderer, диалог и регистрацию;
   сохранить общую оболочку BlockTree и существующие расширения.
6. Edgeless visuals: разделить крупный контроллер по самостоятельным обязанностям,
   убрать статическое оформление controls из TSX.

EventManager сохраняет транспортную роль: определить view, собрать событие,
найти обработчики, вызвать расширение, применить результат. KeyboardManager
сохраняет семантику клавиш. Новая система middleware и приоритетов не нужна.

## Рассмотренные альтернативы

- Только разнести файлы и CSS: дешевле, но длинные hooks и скрытое состояние
  останутся. Используем как первый шаг, не как окончательную архитектуру.
- Отдельный браузерный пакет и тонкий React-адаптер: возможное дальнейшее
  направление после проведения границ внутри пакета; сейчас не требуется.
- Class components: не решают смешение обязанностей и не выбраны.

Состояние инструмента остаётся общим между view, а документные операции используют
API конкретного view. Конструктор editable не подключает listeners во время render.

Новых зависимостей, базовых классов и реестра сервисов не добавлено.
EventManager, slots и уже существующие контроллеры сохраняют свои обязанности.
Изменения ограничены React-пакетом и этим отчётом; demo и core не изменялись.

## Как продолжать работу

- Для изменения поведения editable начинать с `BlockEditingController`, а hook
  менять только при изменении React-подписок или подключения effects.
- Для TODO-операций использовать `TodoItemActions`; renderer отвечает за UI и
  локальное открытие диалога. Prompt conversion принадлежит своему контроллеру.
- Для выбора инструмента и defaults — `EdgelessToolState`; для изменения
  элементов документа — существующий `EdgelessVisualController`.
- Для согласования карточек — `reactEditor.blockElements`; не создавать
  отдельные очереди или настройки в расширениях и отдельных view.
- При новых стилях обращаться к `packages/react-rivto-editor/docs/styling.md`.
  Feature controls находятся в том же utility layer, что и shadcn; `[data-slot]`
  уточняет приоритет над primitive defaults. Никаких правок vendored-компонентов
  или `!important` не требуется. Existing utility-based компоненты вне этих
  восьми controls можно переносить при следующем изменении их собственной функции.

## Следующий шаг: API конкретного отображения

Убираем публичный `events.runInView` и явные обёртки из расширений.
Selection получает явный root для чтения/восстановления и явный events для
отложенных запросов. Clipboard и slash команды получают API конкретного view.
Slash callback получает `reactEditor` этого view вместе с blockId.

Первоначально планировался промежуточный этап с внутренним `withViewRoot`.
После уточнения пользователя принято полностью удалить временный контекст,
включая этот метод и `operationRoot`. Реализация ниже завершает этот перенос.


## Выполнено: явная привязка к view вместо runInView

Удалены `runInView`, `withViewRoot` и `operationRoot`. Поиск по исходникам
`packages/`, `demo/` и `app/` не находит оставшихся вызовов или реализаций.
Event dispatch передаёт получателя через `event.reactEditor` и `event.root`;
он больше не меняет root общего runtime на время вызова обработчика.
Реально активное отображение остаётся состоянием фокуса, а не контекстом стека.

Изменения по владельцам:

- `DocumentViewRegistry` читает surface по переданному root. `EventManager`
  собирает событие из зарегистрированного API конкретного отображения.
- `ReactSelectionManager.createViewApi(reactEditor)` связывает DOM чтение, восстановление
  и очередь с конкретным root. Отложенные callbacks вызываются напрямую;
  удаление/замена root отменяет запрос. Общая модель selection сохранена.
- `EditorViewController` собирает привязанные selection, clipboard и slash API.
  Реестры, история и документные менеджеры остаются общими.
- `SlashCommandContext` теперь содержит `reactEditor`. Callback должен
  использовать его для операций, зависящих от отображения. Встроенная команда
  дублирования переведена на этот API. Общий менеджер захватывает активный
  view при вызове; сохранённый API view не следует последующим сменам фокуса.
- Clipboard создаёт локальный pipeline из текущих зарегистрированных стратегий.
  Core-алгоритмы повторно используются, а `ViewPasteStrategy.createViewStrategy(editor)`
  явно привязывает DOM-зависимую стратегию к получателю. Вложенная вставка
  не изменяет ни внешний pipeline, ни глобальный реестр. Конструирование
  локального core clipboard создаёт несколько короткоживущих объектов на paste;
  новый кеш или изменение core API для этого не вводились.
- Clipboard с отсутствующим выделением view передаёт явно пустую selection.
  `undefined` ранее заставлял core использовать каретку другого отображения.
  Новый тест сначала воспроизвёл изменение `A` в `AUnfocused paste`, а после
  исправления подтверждает сохранение текста исходного блока.
- History, indent, merge, создание/удаление блоков и clipboard получают API из
  события. Жест текстового выделения сохраняет свой editor/root, а transform —
  свой root. Таймеры и preview cleanup используют владельца жеста.
- TODO prompt, slash menu и collapse больше не окружают операции обёрткой.
  Подписчик collapse явно выбирает активное отображение для ремонта текущего
  выделения после документных изменений; root при этом не переключается.

Пример для расширения:

```ts
reactEditor.events.register({ id: "example.input", type: "input" }, (event) => {
  const editor = event.reactEditor;
  queueMicrotask(() => {
    // Operations retain the receiving view instead of reading another view's root.
    editor.selection.readDOM();
  });
  return false;
});

reactEditor.slashCommands.register({
  id: "example.action",
  title: "Example action",
  execute: ({ reactEditor, blockId }) => {
    reactEditor.blocks.updateBlock(blockId, { content: "Example" });
  },
});
```

Это изменение публичного API: старые вызовы `events.runInView` нужно удалить,
а DOM-зависимую работу выполнять через API события/команды или сохранённого
view. Новое поле slash context передаётся менеджером автоматически. Не следует
сохранять общий runtime вместо API view для отложенных DOM-операций.

### Единое имя и аргумент фабрик API отображения

Методы менеджеров `forView` переименованы в `createViewApi`. Общий контракт
`ViewApiFactory<T>` задаёт аргумент `ReactEditorView` и тип возвращаемого API.
`ReactEditorView` расширяет `ReactEditor` обязательным полем `view`: оно содержит
идентичность отображения, доступ к DOM-корню и владение очисткой регистраций.
Events и keyboard используют `reactEditor.view`, selection — `reactEditor.events`,
clipboard и slash — операции переданного редактора.

`EditorViewController` сначала создаёт объект редактора с getters для собираемых
менеджеров, затем events, keyboard, selection, clipboard и slash. Фабрики не
выполняют пользовательские команды при сборке. Events готов до создания selection.
Общие регистрации, документ и поведение операций сохраняются; обратная ссылка на
редактор остаётся осознанно, согласно выбранному объёму изменения.

Отдельный метод стратегии вставки называется `createViewStrategy`: он возвращает
алгоритм вставки, а не API менеджера. Его аргумент остаётся `ReactEditor`, поскольку
вставка доступна и через общий runtime без владельца конкретного отображения.

Изменение требует обновить внешние вызовы старого имени и реализации стратегий.
Это переименование и унификация сборки, без изменения алгоритмов взаимодействия;
повторное измерение времени клавиатурных операций здесь не применялось.

замеры производительности не запускались: алгоритмы взаимодействия не менялись.

### Выполнено: runtime документа и редактор отображения

Актуальная архитектура заменяет описанный выше промежуточный `createViewApi`.

- `editor-runtime.ts`: `EditorRuntime` создаёт общие менеджеры, устанавливает
  расширения один раз и управляет их очисткой. `createEditorRuntime` заменяет
  прежнюю фабрику `createReactEditor`. Model selection остаётся общим core state.
- `react-editor.tsx`: класс `ReactEditor` получает runtime и владельца отображения.
  Конструктор создаёт локальные events, keyboard, DOM selection, clipboard и slash.
  Блоки, история, определения и реестры передаются без копирования.
- `EditorViewController`: приобретение/освобождение документа, состояния загрузки,
  границы поддерева и mounted lifecycle. Большой объект реализации API удалён;
  контроллер создаёт экземпляр `ReactEditor`.
- `ViewEventManager` и `ViewKeyboardManager`: локальные регистрации используют
  идентичность и cleanup отображения; native listeners и настройки общие.
- `ReactSelectionManager`: DOM адаптер принадлежит отображению. Проверка активной
  occurrence и границы поддерева перенесена сюда из контроллера; кеш проверки
  сохраняется по immutable selection snapshot и ревизии дерева.
- `ViewClipboardManager` и `ViewSlashCommandManager`: выполнение использует

  общий clipboard pipeline требует явный редактор назначения. Автоматический
  выбор активного отображения внутри этих операций удалён.

### Общий контракт runtime и отображения

`SharedEditorApi` через один `Pick<EditorViewApi, ...>` описывает общие менеджеры
документа, регистрации и подписку. `EditorRuntime` явно реализует этот контракт;
`EditorViewApi` совместим с ним структурно. Тип экспортируется из пакета.
DOM-события, selection, clipboard/slash execution и destroy в него не входят:
их контракты у runtime и отображения различаются.

Общие операции вставки разделителя и drop-контекст используют `SharedEditorApi`.
`BlockElementProjection` принимает конкретный `EditorRuntime`, который ей владеет.
Проверка принадлежности блока карточке и чтение keyboard selection получают
`BlocksCapability` напрямую. Контекст привязанного slash manager теперь записан
явно как `{ blockId: string }`; сигнатура вызовов и подстановка отображения сохранены.

Перенос между документами использует один локальный `BlockTransferEditor`,
выделенный через `Pick<SharedEditorApi, "blocks" | "history" | "getDocument">`.
Это намеренно более узкий контракт: существующие вызовы работают также с core
редактором без React-регистраций. Pick для координат, частичных данных и ограничения
доступа к lifecycle сохранены. Объединения runtime/view там, где нужны разные
контракты selection и interaction managers, также сохранены.

Изменения уточняют типы и передаваемые зависимости, не меняя алгоритмы или объём
работы на документе. Повторные замеры взаимодействий не требуются; проверяются
существующие unit-тесты, типы, lint и сборки. Stage не изменяется.
