# Глава 00. Простая модель Undo

## 1. Что пользователь ожидает от Undo

Представим документ:

```text
Hello
```

Пользователь печатает `!`:

```text
Hello!
```

После Undo он ожидает снова увидеть:

```text
Hello
```

На уровне интерфейса всё выглядит как «верни старое значение». Но внутри
collaborative editor задача сложнее:

- параллельно другой пользователь мог изменить другой блок;
- блок мог быть перемещён в дереве;
- текст хранится не как одна обычная строка, а как CRDT text;
- одна пользовательская операция может изменить несколько CRDT-контейнеров;
- чужое удалённое изменение нельзя случайно отменить локальной кнопкой Undo.

Поэтому полная копия документа «до» и «после» — плохая модель.

## 2. Почему не массив snapshots

Наивная реализация могла бы выглядеть так:

```ts
const history = [snapshotBefore, snapshotAfter];
```

У неё сразу появляются проблемы.

### Проблема 1. Память

Если документ содержит 10 мегабайт, а пользователь напечатал один символ,
копирование всего документа ради одного символа очень дорого.

### Проблема 2. Совместная работа

Допустим:

1. Анна добавила `!` в первый блок.
2. Борис удалённо добавил новую картинку во второй блок.
3. Анна нажала Undo.

Восстановление старого snapshot Анны могло бы удалить картинку Бориса. Это не
Undo локального действия, а откат всего мира назад.

### Проблема 3. Идентичность CRDT

CRDT хранит не только видимое значение, но и служебную историю операций,
которая позволяет объединять параллельные изменения. Простая подмена JSON не
равна корректному обратному CRDT-изменению.

## 3. Что хранит CRDT Undo manager

Полезная упрощённая модель:

```text
обычный history snapshots:  "сохрани всё старое состояние"
CRDT undo history:           "запомни локальные операции и их обратный эффект"
```

Например, вместо полной копии документа история знает, что локальная операция
вставила `!` в конкретную CRDT text structure. Undo применяет обратное действие
к этой операции, сохраняя независимые изменения других участников.

Настоящие внутренности Yjs сложнее, но для работы с Rivto этой модели
достаточно.

## 4. Четыре понятия

### Operation

Низкоуровневое изменение CRDT: вставка текста, удаление элемента массива,
запись поля map.

### Transaction

Группа операций, которая выполняется как одно атомарное изменение документа.

Пример форматирования Markdown:

```text
Alpha
```

Для bold нужно вставить две пары `**`:

```text
**Alpha**
```

Это две вставки, но пользователь воспринимает их как одну команду. Rivto
выполняет обе внутри общей транзакции.

### Origin

Метка автора или источника транзакции. В Rivto `DocumentModelImpl` создаёт
собственный `Symbol` и помечает им локальные модельные транзакции.

### Scope

Конкретная CRDT-структура, изменения которой отслеживает Undo manager. Можно
думать о scope как о границе вопроса: «историю каких контейнеров мы вообще
собираем?»

## 5. Что является частью истории Rivto

`DocumentModelImpl.undoScopes` включает четыре top-level структуры:

```text
blocks       данные блоков и их content/layout/props
roots        порядок корневых блоков
links        связи между блоками
pluginData   document-level данные plugins
```

Вложенные CRDT-структуры, принадлежащие этим scopes, также отслеживаются Yjs.

Локальные presentation states не входят в document history:

- selection;
- активный mode;
- zoom React renderer;
- открытое slash menu;
- browser focus.

Поэтому Undo текста не обязано восстанавливать старый курсор или zoom.

## 6. Что означает «локальная история»

`Y.UndoManager` создаётся с `trackedOrigins`, содержащим только
`document.origin`.

Упрощённо:

```text
транзакция с document.origin  → попадает в локальную history
remote transaction            → не попадает в локальную history
```

Удалённое изменение всё равно появляется в документе и React его показывает.
Просто нажатие Undo текущего пользователя не выбирает его как собственный
последний шаг.

## 7. Undo и command — разные уровни

Command отвечает за пользовательское намерение:

```text
"сделать текст bold"
```

DocumentModel переводит это намерение в модельные изменения:

```text
"вставить suffix, вставить prefix"
```

CRDT transaction объединяет низкоуровневые изменения:

```text
"эти вставки были атомарной операцией с таким origin"
```

Undo manager умеет обратить записанную CRDT-транзакцию.

```text
CommandRegistry
      ↓
EditorRuntime command handler
      ↓
DocumentModelImpl.transact
      ↓
CRDTDoc.transact(origin)
      ↓
Y.UndoManager history
```

## 8. Частая ошибка в понимании

`history.undo()` не вызывает обратный handler для последней команды.

В Rivto нет таблицы вида:

```ts
{
  "block.insert": "block.remove",
  "text.insert": "text.delete",
}
```

Такая таблица быстро сломалась бы на:

- автоматически созданных ID;
- удалённых поддеревьях;
- links;
- одновременных удалённых изменениях;
- сложной structured paste.

Обратную CRDT-операцию знает adapter и его Undo manager.

## 9. Итог главы

Запомните пять утверждений:

1. Undo не восстанавливает полный JSON snapshot.
2. Историю низкоуровневых операций ведёт CRDT adapter.
3. Transaction объединяет связанные изменения.
4. Origin отделяет локальные операции от удалённых.
5. Scope определяет, какие части collaborative document отслеживаются.
