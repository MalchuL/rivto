# Глава 00. Что браузер называет выделением

Начнём без Rivto и без React. Сначала нужно понять, какие данные даёт сам
браузер.

## 1. HTML и DOM — не одно и то же

HTML — текст:

```html
<div>Hello <strong>world</strong></div>
```

После загрузки браузер создаёт из него дерево объектов — DOM:

```text
HTMLDivElement
├── Text("Hello ")
└── HTMLElement <strong>
    └── Text("world")
```

`Text("Hello ")` и `Text("world")` — разные DOM-узлы, хотя на экране это одна
строка. Для selection это очень важно: браузер хранит позицию не как «седьмой
символ div», а как пару:

```text
конкретный DOM-узел + offset внутри этого узла
```

Например, позиция после `wo` может выглядеть так:

```ts
{
  node: Text("world"),
  offset: 2,
}
```

Offset означает позицию между символами:

```text
|w|o|r|l|d|
0 1 2 3 4 5
```

## 2. Что делает contenteditable

Обычный `<div>` нельзя редактировать. Атрибут `contenteditable="true"` говорит
браузеру:

> Пользователь может поставить сюда курсор и менять DOM с клавиатуры.

```html
<div contenteditable="true">Hello</div>
```

При вводе буквы сначала браузер сам меняет DOM. Только после этого React
получает `input` event. Поэтому в редакторе есть два состояния текста:

```text
текст в DOM, который пользователь видит прямо сейчас
текст в DocumentModel, который является данными приложения
```

Они должны быть синхронизированы, но обновлять DOM после каждой буквы опасно:
если заменить текстовый DOM-узел, браузер потеряет старую позицию курсора.

## 3. Курсор — тоже selection

Для браузера нет отдельной сущности «курсор». Курсор — это выделение нулевой
длины.

```text
Hello| world
     ▲
anchor и focus находятся в одной позиции
```

Такое выделение называется **collapsed selection**.

Если пользователь выделил `world`, позиции различаются:

```text
Hello [world]
      ▲     ▲
   anchor  focus
```

## 4. Объект Selection

Текущее выделение страницы можно получить так:

```ts
const selection = window.getSelection();
```

Нас интересуют четыре поля:

```ts
selection.anchorNode;
selection.anchorOffset;
selection.focusNode;
selection.focusOffset;
```

### Anchor

`anchor` — место, где пользователь начал жест.

Для мыши это обычно точка `pointerdown`. Для Shift+Arrow это неподвижный конец
предыдущего выделения.

### Focus

`focus` — активный конец. Он двигается вместе с мышью или клавиатурой.

В коде Rivto portable-аналог `focus` называется `head`. Названия отличаются,
но смысл одинаков:

```text
browser Selection       Rivto TextSelection
anchor                  anchor
focus                   head
```

## 5. Направление выделения

Рассмотрим два блока:

```text
Первый блок
Второй блок
```

Пользователь может начать в первом и вести мышь вниз. Тогда anchor расположен
раньше focus.

Он может начать во втором и вести мышь вверх. Визуально можно выделить тот же
текст, но anchor будет во втором блоке, а focus — в первом.

Это направление нельзя терять. Оно определяет:

- какой конец продолжит двигаться при Shift+Arrow;
- где пользователь ожидает увидеть активный caret;
- как корректно восстановить браузерное выделение.

## 6. Selection и Range — разные объекты

`Selection` описывает пользовательское выделение и сохраняет направление.

`Range` описывает упорядоченный участок DOM:

```ts
const range = document.createRange();
range.setStart(startNode, startOffset);
range.setEnd(endNode, endOffset);
```

У `Range` начало обязано находиться раньше конца в DOM. Он не хранит «я начал
снизу и повёл вверх». Поэтому нельзя заменить всё состояние selection одним
`Range`, если направление важно.

Rivto использует оба:

- `Selection.setBaseAndExtent()` — чтобы попытаться показать направленное
  выделение браузеру;
- `Range` — чтобы измерять offsets, создавать подсветку и работать там, где
  направление не важно.

## 7. Событие selectionchange

Когда браузер меняет курсор или выделение, `document` отправляет событие:

```ts
document.addEventListener("selectionchange", listener);
```

Событие может прийти после клика, drag, клавиатурной команды или программного
изменения selection.

Важная деталь: событие асинхронное относительно некоторых действий. Например,
`paste` может прийти раньше, чем приложение получит самый свежий
`selectionchange`. Поэтому перед Paste Rivto дополнительно читает native
selection прямо в обработчике Paste.

## 8. Capture и bubble у событий

DOM-событие проходит дерево в две основные фазы:

```text
document → родитель → target       capture
target → родитель → document       bubble
```

`onPointerDownCapture` в React вызывается на пути к target, до обычной реакции
вложенного `contenteditable`. Rivto использует capture, чтобы запомнить точную
стартовую позицию выделения до того, как браузер начнёт самостоятельно менять
native selection.

Обычный `onClick` приходит позже в bubble-фазе. В edgeless-режиме это важно:
клик по тексту внутри карточки может подняться до самой карточки. Если не
проверить target, карточка выберет объект и уничтожит только что созданный
текстовый caret.

## 9. Pointer events

Для drag Rivto слушает:

- `pointerdown` — начало;
- `pointermove` — изменение активного конца;
- `pointerup` — завершение.

Глобальный `window` listener нужен потому, что после начала drag указатель
может выйти за DOM-элемент, на котором был `pointerdown`.

Используются pointer events, а не только mouse events: Chromium во время
нативного text-selection drag иногда задерживает `mousemove`, но продолжает
отправлять `pointermove`.

## 10. Почему несколько contenteditable сложнее одного

Каждый блок Rivto имеет собственный editable host:

```html
<div data-rivto-block="A">
  <span class="rv-block-content" contenteditable="true">Alpha</span>
</div>
<div data-rivto-block="B">
  <span class="rv-block-content" contenteditable="true">Beta</span>
</div>
```

Это удобно для блоков, но браузеры по-разному работают с диапазоном между A и
B:

- могут ограничить caret активным `contenteditable`;
- могут хранить range, но подсвечивать только один host;
- могут поздно отправить `selectionchange`;
- при выделении снизу вверх могут временно сообщить неправильные endpoints.

Поэтому Rivto сам вычисляет cross-block endpoints, хранит их независимо от DOM
и отдельно дорисовывает подсветку.

## 11. UTF-16: почему offset иногда не равен числу символов

JavaScript-строки и DOM Range используют UTF-16 code units.

```ts
"A".length;  // 1
"😀".length; // 2
```

Значит offset 2 может быть положением после одного emoji. Rivto намеренно
использует ту же систему, что JavaScript и DOM, иначе перевод позиции между
моделью и браузером был бы неоднозначным.

Для пользователя это всё ещё выглядит как один символ. Не пытайтесь заменить
offset на индекс Unicode code point только в одной части системы: тогда DOM и
DocumentModel начнут считать позиции по-разному.

## 12. Минимальный итог главы

Перед следующей главой важно понимать:

1. DOM — дерево объектов, а не HTML-строка.
2. Browser position — это DOM-узел плюс offset.
3. Курсор — collapsed selection.
4. Anchor — начало жеста, focus/head — активный конец.
5. Направление выделения нужно сохранять.
6. `Range` сортирует границы и не заменяет направленный `Selection`.
7. `contenteditable` сначала меняет DOM, затем сообщает приложению.
8. Несколько editable hosts требуют собственного selection-слоя редактора.
