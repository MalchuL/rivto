# Большой документ: профиль и план исправлений

Дата: 2026-10-08. Исследована production-сборка demo в Chromium, page-режим,
настройки по умолчанию, без виртуализации. Реальные Tab / Shift+Tab, прогрев,
пять измерений каждого действия. Проверены вложенность, selection и DOM-фокус.
Загрузка документа не входит в измерение. Два кадра браузера — ориентир
задержки отображения, а не гарантия завершения всех отложенных действий.

| Документ | Синхронная операция с подписчиками | До двух кадров |
| --- | --- | --- |
| 57 блоков | 2,1 мс | 31 мс |
| 3057 блоков (`?repeat=200`) | 35–36 мс | 320–345 мс |

Указаны медианы для двух направлений. На большом документе отдельные замеры:
301–388 мс. Повторный прогон восстановленного кода: медианы 309–321 мс.

## 1. Нумерация demo

Место: `demo/src/extensions/block-number.tsx`, `useBlockOrdinal`.
Каждая строка подписана на всю Map номеров через useSyncExternalStore.
Смена Map вызывает 3062 рендера номеров на одно нажатие.

Решение: snapshot конкретного блока со стабильной ссылкой, пока номер и
глубина не изменились. Общий расчёт номеров оставить единым для документа.
Эксперимент: 2 рендера вместо 3062, 223–226 мс вместо 337–342 мс;
видимая нумерация сохранена.

## 2. DOM-выделение

Место: `packages/react-rivto-editor/src/managers/selection/editor-dom-selection.ts`,
`createDOMSelection`, чтение и восстановление native selection.
Даже каретка вызывает сбор всех блоков и поиск content внутри каждого:
около 9172 вызовов поиска `[data-block-content]` за действие.

Решение: использовать известные концы выделения и прямой поиск блока для
одноблочного диапазона; полный порядок нужен межблочному диапазону.
Сохранить направление выделения, contentless-блоки, границы вложенных
редакторов и виртуализацию. Объединить повторяющийся поиск DOM-контента.

## 3. Повторные чтения дерева

Семь getBlocks за действие: SelectionManager.set, reconcileDocumentSelection,
расширение collapse, нумерация, согласование canvas и повторная публикация
каретки. Три чтения внутри транзакции обходят кеш: примерно 9184 чтения узлов.

Места: `packages/rivto-editor-core/src/managers/selection-manager/selection-manager.ts`,
`packages/rivto-editor-core/src/editor/rivto-editor.ts`,
`packages/react-rivto-editor/src/extensions/built-ins/page/collapse/register.ts`.

Решение: проверять выбранные ID и цепочки родителей, использовать порядок
ID вместо рекурсивных снимков там, где данные блоков не нужны. Объединять
проверку и упорядочивание selection в его владельце. Не включать кеш снимков
внутри транзакций без обеспечения актуальности данных.

## 4. Размер DOM — вне текущих исправлений

Без виртуализации: 68209 DOM-элементов. Профиль показал затраты на стили,
подготовку отрисовки и browser hit testing; один пересчёт стилей затрагивал
около 10000 элементов. С существующей виртуализацией: 1324 элемента,
49–51 мс до двух кадров; синхронная работа всё ещё около 25 мс.

По решению пользователя виртуализацию не меняем.

## 5. Согласование canvas

Место: `packages/react-rivto-editor/src/elements/block-element-projection.ts`,
`reconcileBlockElements`. На локальное изменение строится полное дерево,
матрица «сегмент × карточка» и выполняется глобальное сопоставление.
Диагностическое отключение сократило задержку до 271–296 мс.

Решение: читать только необходимые корневые данные, сохранять уже однозначные
соответствия и не выполнять глобальное сопоставление, когда оно не нужно.
Сохранить ID карточек, разделение/слияние, undo и согласованность canvas.
Отключение reconciliation не является допустимым исправлением.

## Реализованные изменения

- `demo/src/extensions/block-number.tsx`: snapshot подписки содержит только
  номер и глубину текущего блока. При равных значениях сохраняется прежняя
  ссылка, поэтому публикация новой общей Map не перерисовывает все номера.
- `packages/rivto-editor-core/src/managers/block-manager/block-manager.ts`:
  `getOrderedIds` упорядочивает уникальные существующие ID через пути предков
  и позиции среди соседей. Кеши локальны одному вызову, поэтому не требуют
  отдельной инвалидации при undo или удалённом изменении.
- `SelectionManager.set` и `RivtoEditor.reconcileDocumentSelection` используют
  этот общий метод. `resolveBlockSelection` читает только выбранные поддеревья.
- `navigation/utils/collapsed-selection.ts`: проверяются предки выбранных
  блоков до границы текущего embedded view. Коллапс выше границы не скрывает
  отдельно отображаемый корень. Полный снимок документа больше не нужен.
- `managers/events/document-view.ts`: общий поиск shell и собственного content
  по ID, с исключением вложенных document views. Его используют чтение и
  восстановление DOM-выделения. Одноблочный диапазон не перечисляет документ;
  для межблочного диапазона content индексируется одним проходом.
- `elements/block-element-projection.ts`: читаются только корневые узлы.
  Индекс принадлежности блока сегменту заменяет перебор всех пар. Независимые
  группы сопоставляются отдельно; для единственной пары матрица не нужна.
  Внутри конкурирующей группы сохранён глобальный алгоритм и прежние веса,
  определяющие сохранение карточек, split/merge и геометрии.

Виртуализация, сохранённые схемы документов и stage не изменялись.

## Результаты после исправлений

Тот же Chromium, production-сборка, viewport 1280×1000, пять замеров после
прогрева. Нумерация и остальные расширения включены, виртуализация выключена.
Большой документ по-прежнему содержит 3057 блоков и 68209 DOM-элементов.
Здесь «до двух кадров» сохраняет ту же методику, что и исходное исследование.

| Документ / действие | Синхронно до → после, мс | До двух кадров до → после, мс | Диапазон после, мс |
| --- | --- | --- | --- |
| 57 блоков / Tab | 2,1 → 1,2 | 31,2 → 31,7 | 31,1–31,9 |
| 57 блоков / Shift+Tab | 2,1 → 1,3 | 31,0 → 31,4 | 31,1–31,6 |
| 3057 блоков / Tab | 36,4 → 13,4 | 345,2 → 182,1 | 170,0–215,5 |
| 3057 блоков / Shift+Tab | 34,6 → 13,8 | 320,3 → 201,0 | 196,5–223,4 |

Синхронные диапазоны после: 1,0–1,4 / 1,2–1,7 мс на обычном документе,
12,6–16,2 / 13,1–14,4 мс на большом. JavaScript на большом документе:
медианы 177/170 → 47/47 мс. Метрики пересекаются, складывать их нельзя.

Отдельный инструментированный прогон подтвердил:

- getBlocks: 7 → 1 на действие, оставшееся чтение нужно общей нумерации;
- querySelectorAll('[data-block-content]'): около 9172 → 0 в сценарии каретки;
  прямые поиски content через querySelector остаются;
- чтения узлов внутри транзакции: около 9184 → около 3072.

Инструментирование использовалось для подсчёта вызовов; его длительности не
смешивались с чистыми замерами. Результаты: `/tmp/rivto-profile/fixed-small.json`,
`fixed-large.json`, `fixed-counts.json`.

Стоимость стилей, фокуса и отрисовки большого DOM остаётся. Изменение
виртуализации исключено из этой задачи по решению пользователя.
