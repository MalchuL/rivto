# Перетаскивание блоков: предложенные и реализованные изменения

**Статус: реализовано в текущих изменениях рабочей ветки.** Документ описывает
предложенный подход, фактическую реализацию и результаты проверки. Это отчёт
о выполненном рефакторинге, а не список будущих задач.

## Исходная проблема

Старая логика сначала выбирала блок под указателем или рядом с ним, затем
передавала причину выбора в отдельную логику размещения. Та повторно
интерпретировала геометрию: «до блока», «после блока» или «внутрь».

Между этапами терялась информация о конкретном промежутке между соседями.
Небольшое смещение указателя могло выбрать другую строку, другого родителя
или другой уровень вложенности. Особенно заметно это было между контейнерами:
указатель оставался около одной границы, а подсветка и вставка переходили
к другой паре блоков.

Дополнительная проблема — смешение трёх разных вопросов:

- Как расположены дети контейнера: вертикально, горизонтально или сеткой?
- Можно ли использовать всю площадь блока как область приёма?
- Какие типы блоков допустимы у будущего родителя?

Например, горизонтальная раскладка сама по себе не означает, что обычный
параграф можно вставить рядом с колонками. Прежняя проверка получала целевой
блок и ID источников, но не точное место вставки. Она не могла однозначно
отличить вставку внутрь блока от вставки рядом с ним.

## Что было предложено и что сделано

| Предложение | Реализация |
| --- | --- |
| Сразу определять место вставки, а не промежуточный «попавший под курсор блок» | Resolver возвращает `between` с родителем и соседями либо `inside` с принимающим родителем |
| Искать место в пределах иерархии | Resolver обходит списки непосредственных детей; глобальный поиск ближайшей строки удалён |
| Зафиксировать принадлежность границ контейнеров | Узкая внешняя граница контейнера выбирает его соседний промежуток на корневом и вложенных уровнях |
| Отделить геометрию от допустимости перемещения | Добавлены `dropChildTypes`, `dropParentTypes` и проверка полного назначения |
| Использовать один результат для подсветки и перемещения | Сохраняется показанное назначение; при отпускании оно проверяется повторно без выбора нового места |
| Убрать отдельную геометрию для переноса между документами | Локальное и междокументное перетаскивание используют `resolveSurfaceDrop` |
| Сохранить клавиатурное перетаскивание | Центр перемещённого прямоугольника источника передаётся в общий resolver с клавиатурной политикой |
| Сохранить обычную вложенность | Центр текстовой строки допускает вложение; горизонтальное движение в доступных промежутках выбирает глубину |
| Проверять поведение через границы, а не только отдельные точки | Добавлены проходы указателя с шагом в один пиксель и проверки индикатора вместе с итоговым порядком блоков |

Два поведения были отдельно согласованы перед реализацией:

1. Фон Kanban/Columns вне колонок не принимает обычный блок. Автоматического
   перенаправления в ближайшую колонку нет.
2. Перетаскивание на середину обычного текстового блока по-прежнему может
   вложить источник в этот блок.

## Как теперь определяется место вставки

Путь обработки состоит из следующих шагов:

1. **Измерение поверхности.** Собираются видимые блоки, границы их строк
   и поддеревьев, принадлежность родителю и свойства layout из view.
2. **Подготовка дерева назначения.** Перемещаемые поддеревья исключаются
   из доступных мест. Геометрия и дерево читаются заново при расчёте,
   в том числе после прокрутки.
3. **Обход списков детей.** Сначала проверяется промежуток или граница
   на текущем уровне. Внутренняя область контейнера рассматривается
   в контексте его собственных детей.
4. **Проверка назначения.** Будущий родитель проверяет все переносимые
   корневые блоки. Запрет не превращается в поиск произвольной дальней цели.
5. **Отображение.** Для промежутка resolver возвращает координаты линии.
   Для вставки внутрь подсвечивается принимающий блок.
6. **Завершение жеста.** Проверяется, существуют ли источники и сохраняется ли
   показанное назначение. Если промежуток изменился или назначение больше
   не разрешено, перемещение отменяется.

Геометрические правила остаются разными для вертикального списка,
горизонтального списка и сетки. Они описывают раскладку, а не конкретные
типы Kanban, Columns или Table. В общем resolver нет переключателя
по именам этих контейнеров.

### Пример стабильного промежутка

Для списка `A, B, C` место между `A` и `B` представляется так:

```ts
{
  kind: "between",
  parentId: "container",
  previousId: "A",
  nextId: "B",
  depth: 1,
}
```

Пока указатель остаётся в области этого промежутка на выбранном уровне,
соседи остаются `A` и `B`. Их не нужно повторно угадывать по ближайшей строке.
Переход в другую область или явный выбор доступной глубины в обычном outline
может изменить назначение.

Если до отпускания указателя другой участник вставил `X` между `A` и `B`,
проверка обнаружит, что сохранённые соседи больше не смежные. Редактор
отменит этот drop, а не выберет незаметно промежуток `A–X` или `X–B`.

## Новые и изменённые контракты

### Назначение: `BlockDropDestination`

```ts
type BlockDropDestination = {
  readonly kind: "between";
  readonly parentId: string | null;
  readonly previousId: string | null;
  readonly nextId: string | null;
  readonly depth: number;
} | {
  readonly kind: "inside";
  readonly parentId: string;
};
```

`parentId: null` означает корневой список документа. У `between` отсутствие
предыдущего или следующего соседа обозначает начало или конец списка.
`inside` означает добавление в конец списка детей выбранного родителя.

Формы `between` и `inside` существовали в прежней реализации. Рефакторинг
сделал их основой всего расчёта и контракта проверки; дополнительная цепочка
«причина попадания → намерение → назначение» больше не нужна.

### Возможности view

| Свойство | Назначение |
| --- | --- |
| `dropAxis` | Раскладка непосредственных детей: `vertical`, `horizontal`, `grid` |
| `acceptsDropContainer` | Можно ли использовать полное тело блока, включая пустую область, для приёма |
| `dropChildTypes` | Типы непосредственных детей, разрешённые при перетаскивании; отсутствие списка означает отсутствие этого ограничения |
| `dropParentTypes` | Типы родителей, в которые разрешено перемещать структурный блок |
| `dropPlacement` | Настройки зон и вложенности, включая `allowChildPlacement` |
| `acceptsDrop(context)` | Дополнительная семантическая проверка точного назначения |

Проверка менеджера изменилась:

```ts
// Раньше
views.acceptsDrop(targetId, sourceIds);

// Теперь
views.acceptsDrop(destination, sourceSnapshots);
```

Пользовательский метод view получает `{ reactEditor, destination, sources }`.
`sources` — снимки переносимых блоков, а не ID, которые пришлось бы искать
в документе назначения. Это позволяет проверять типы при переносе между
разными документами. Для группы проверяется каждый переносимый корень.

Метод вызывается на view **будущего родителя**, а не соседнего блока,
рядом с которым проходит указатель. Для корневого назначения используется
общая fallback-view.

### Правила контейнеров

| Родитель | Допустимый непосредственный структурный ребёнок |
| --- | --- |
| Kanban | `kanban-column` |
| Columns | `columns-column` |
| Table | `table-row` |
| Строка Table | `table-cell` |

Структурные дети также объявляют разрешённые типы родителей. Колонки
и ячейки принимают обычное содержимое; Bento сохраняет свободный набор плиток.
У корня Columns приём через тело остаётся отключённым.

**Эти ограничения относятся к drag-and-drop.** Они не добавляют новых
инвариантов в сохраняемую модель документа и сами по себе не запрещают
другим API создавать определённую иерархию. `childOutline: "fixed"`
продолжает отвечать за outline-поведение и не заменяет проверку типов.

## Что удалено и что нужно обновить расширениям

Удалены прежние промежуточные контракты `PointerDropHit`, `PointerDropReason`,
`HitDropIntent`, `DropPlacementInput`, а также передача `PageDragData` между
этапами размещения. Удалены старый pointer-picker, таблица интерпретации
намерений и отдельный путь геометрического расчёта для междокументного drop.

Индикатор больше не выбирает место по собственной геометрической эвристике:
он отображает линию, рассчитанную resolver. Хранение состояния учитывает
изменение координат линии, поэтому прокрутка может обновить её даже при
неизменных родителе и соседях.

Авторам расширений, использовавшим старый контракт, необходимо:

1. Перевести `acceptsDrop` с `targetId/sourceIds` на `destination/sources`.
2. Проверять будущего родителя, а типы источников читать из переданных снимков.
3. Объявить `dropChildTypes` и `dropParentTypes` для структурных контейнеров.
4. Не использовать совпадение осей источника и назначения как разрешение
   на перемещение.

Пример декларации существующей пары Kanban:

```ts
class KanbanView extends ContainerBlockView {
  override readonly dropAxis = "horizontal" as const;
  override readonly dropChildTypes = [KANBAN_COLUMN_BLOCK_TYPE];
}

class KanbanColumnView extends ContainerBlockView {
  override readonly dropParentTypes = [KANBAN_BLOCK_TYPE];
}
```

Формат сохранённых документов не менялся; миграции данных не добавлялись.
Перемещения по-прежнему выполняются через существующие менеджеры и механизм
транзакций/undo. Новых зависимостей нет.

## Дополнительные исправления

При проверке клавиатуры обнаружилась гонка: dnd-kit отправляет `dragmove`
до применения новой позиции, а саму позицию обновляет в микрозадаче.
Если promise рендера уже завершён, обработчик мог прочитать старые координаты.
Теперь продолжение обработки планируется так, чтобы читать обновлённую позицию.

Геометрия линии хранится в координатах viewport, а при отображении переводится
в локальные координаты элемента с учётом масштаба. Проверен вариант edgeless
с масштабом 80%.

## Проверки и ограничения результатов

На момент завершения реализации:

- React Jest: **45 наборов, 222 теста — успешно**.
- Проверки типов, lint, сборка React-пакета, сборка demo и `git diff --check`
  завершились успешно.
- Проверены Chromium и Firefox: корневые и вложенные границы, фон Kanban/Columns,
  пустые колонки, Bento, перестановка структурных блоков, клавиатура,
  отмена жеста, прокрутка, перенос между документами и undo.
- Новые браузерные проверки проходят через границы с шагом в один пиксель,
  сравнивают положение линии и итоговый порядок блоков в page/edgeless.
- После исправления клавиатурной гонки повторные клавиатурные прогоны прошли
  в обоих браузерах.

В последнем широком целевом прогоне прошли 139 из 140 проверок. Оставшаяся
проверка auto-scroll ожидала, что DOM-владелец линии всегда совпадает
с блоком под указателем. Для канонического промежутка это неверно: линией
может владеть предыдущее поддерево на выбранной глубине. Проверку изменили
на близость линии к указателю; для подсветки `inside` сохранено точное
совпадение блока. После этого все шесть повторов этой проверки прошли
в Chromium/Firefox. Весь широкий набор после изменения только этой проверки
повторно не запускался.

Также исправлен сценарий Kanban: перед наведением на колонку тест прокручивает
её в видимую область. Ранее координаты могли находиться за обрезанной границей
доски, а старый поиск ближайшего блока всё равно находил невидимую колонку.

Полный браузерный набор нельзя считать полностью зелёным. Отдельно на исходном
коде до рефакторинга воспроизведены сбои clipboard, переполнения Kanban
в edgeless, доступности ручки в модальном Kanban и stationary-scroll в Firefox.
Они не объявлены исправленными этим изменением и не были включены в успешную
целевую проверку как уже решённые.
