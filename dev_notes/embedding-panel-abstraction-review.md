# Embedding and React panel boundaries

This review describes the working tree on 2026-11-08, including existing uncommitted changes. It proposes changes only; no implementation is included.

## Findings

1. **The React panel recognizes a concrete core panel type to choose card projection roots.** In `packages/react-rivto-editor/src/panels/react-panel.ts`, the constructor imports `EmbeddingPanel` and passes `null` as the block root to `editor.blockElements.maintainBlockCards` when `corePanel instanceof EmbeddingPanel`; otherwise it passes `corePanel.rootBlockId`. This is the current equivalent of an `isEmbedding` check: a generic occurrence lifecycle infers a projection policy from a subtype. It also makes equivalent custom `PanelAPI` implementations behave differently and relies on runtime class identity. The branch does not identify the embedding extension: `EditorEmbed` is also used by `BlockModal`.

   The difference is consequential. `BlockElementProjection` interprets the block root as a **parent whose direct children** form card ranges, while `EmbeddingPanel` displays and protects the root itself. Passing the displayed root would project its children instead. Passing `null` selects document block roots; it does **not** mean “disable projection”. With a non-null element root, maintenance can still reconcile persistent cards for that root pair. With null/null, the existing editor-owned document projection is used and the returned cleanup is a no-op. Any replacement must establish the intended behavior for both element-root cases before changing it; silently skipping maintenance or using the embedding root changes behavior.

2. **The projection is acquired by every React panel even though it serves canvas cards.** `ReactPanel` constructs Page and other local managers and unconditionally retains card maintenance, including for the Page-only surface rendered by `EmbeddingBody`. Initial reconciliation can mutate document elements, and the last consumer releases subscriptions. The editor itself separately owns the document-root projection. This mixes occurrence construction with an edgeless concern, but moving it blindly to a mounted canvas could change reconciliation timing, shared consumers, and persisted elements. First determine whether cards must remain synchronized while only Page surfaces are mounted and how an explicit `rootElementId` is intended to work with `EditorEmbed`.

3. **Embedding terminology spans two different responsibilities.** The optional `embeddingExtension` owns reference blocks, lookup, acquisition, recursion prevention, settings, and rendering; `EditorEmbed` and the core `EmbeddingPanel` instead provide a reusable protected-root view, also used by modals without a reference block. The latter behavior is a valid shared capability, not itself evidence that the extension has leaked into the panel. However, its names encourage consumers to associate root inclusion with the reference feature. Consider a name describing the protected root only if changing this public API has a practical benefit; do not rename solely to eliminate the word.

4. **Reference resolution is a shared storage service with an embedding-specific consumer.** `EditorStorage` constructs and destroys `blockReferences`; `EmbeddingBody` uses it through `EditorStorageContext` and separately acquires the resolved source editor. This couples storage to reference lookup even when the extension is absent, but is outside the React panel itself. Before moving it into the extension, inspect other current and intended consumers and preserve shared lookup subscriptions, abort behavior, editor acquisition/release, and storage destruction. An extension-owned resolver is appropriate only if lookup is actually feature-specific; otherwise describe it as a generic block-reference service. Do not add a second resolver per rendered reference.

The `getSurfaceType()` behavior and surface-context checks elsewhere distinguish the actual receiving Page or Edgeless surface from the document mode. Those checks are generic occurrence behavior, even when their comments use embeddings as examples. Likewise, bounded block operations, protected root, per-panel focus and keyboard lifecycle, and shared document selection/history are required independently of the optional reference extension.

## Proposed removal

1. Replace the subtype test with a contract that states the **actual card projection scope**, at the owner that knows it. The existing `PanelBlocksAPI.includeRoot` exposes the root-inclusion policy, so a minimal first candidate is to derive the same block-root argument from `corePanel.blocks.includeRoot` and `corePanel.rootBlockId`, without exposing a new `isEmbedding` flag. Confirm that every include-root panel has the same projection requirements; root visibility alone must not become a permanent proxy if counterexamples exist. If projection policy differs independently, pass the actual projection root or a narrowly defined projection policy from the panel creation boundary instead. Avoid putting React canvas policy into the framework-neutral core solely to remove an import.
2. Trace `EditorPanel` and `EditorEmbed` through `ReactPanelProvider`, `ReactPanel`, `BlockElementProjection`, and destruction. Decide and document when each root pair needs maintenance, including non-null element roots, multiple consumers, missing roots, undo, and editor destruction. Only then consider moving retention to the Edgeless surface or another actual lifecycle owner. Preserve synchronous reconciliation and cleanup unless intentionally changing that contract.
3. Keep reference lookup, acquisition, refresh, and cycle detection in the reference feature; keep protected-root panel behavior reusable. Evaluate storage ownership separately as described above. Narrow dependencies at actual consumers rather than introducing wrappers or duplicate manager fields.
4. Remove stale subtype imports and update public documentation only after the new contract and callers agree. Check extension installation/removal and both `EditorEmbed` callers; do not equate modal views with reference blocks.

## Verification for an implementation

- Add a focused regression with a non-`EmbeddingPanel` implementation of the same panel contract, and cover children-root versus included-root behavior without `instanceof`. Verify both null and non-null element roots and inspect persisted card changes, not just the argument passed to maintenance.
- Cover simultaneous panels sharing a root pair, final cleanup, missing/restored roots, construction failure, and editor destruction. Check that Page-only and Edgeless transitions preserve the agreed reconciliation timing.
- Exercise a reference embedding and a block modal in the real browser, including edits, protected root, selection/focus, undo, and nested or cross-document references. Run relevant Page and Edgeless cases and the repository's required performance workflow; compare before/after when changing projection work.
- Review API ownership independently of tests: the host owns the editor and its document projection; the occurrence owns its local managers and retained maintenance; storage owns acquired editors and lookup until the implementation explicitly changes those boundaries.

This is a source review, not proof that the current projection policy is correct for every configuration. The non-null element-root behavior and the need for maintenance while no canvas is mounted require a decision backed by focused tests before implementation.
