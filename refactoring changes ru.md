Целевая архитектура должна позволять коду взаимодействий работать с **ID блоков, текстовыми позициями, геометрией и операциями редактора**. DOM-элементы остаются внутри браузерных адаптеров и React-компонентов.

Основой остаются существующие менеджеры ядра, модель выделения и алгоритм определения позиции вставки. Предлагаемые изменения добавляют границу поверхности и выделяют управление перетаскиванием. Формат сохранённых документов менять не требуется.

Все интерфейсы ниже — предложение, а не уже реализованный код.

**1. Адаптер поверхности для браузерных операций**

Адаптер представляет одну смонтированную поверхность взаимодействия: страницу, бесконечный холст или редактируемую карточку внутри него.

```
interface SurfaceAdapter {
  /** Принадлежит ли блок этой поверхности. */
  containsBlock(blockId: string): boolean;

  /** Порядок выделения, включая виртуализированные блоки. */
  getSelectionBlocks(): readonly PageVirtualizationSelectionBlock[];

  /** Находит блок по координатам указателя относительно viewport. */
  readBlockIdAtPoint(point: PointerCoordinates): string | undefined;

  /** Находит текстовую позицию по координатам указателя. */
  readPositionAtPoint(
    point: PointerCoordinates,
  ): EditorPosition | undefined;

  /** Возвращает браузерное выделение в формате редактора. */
  readDOMSelection(): Selection | undefined;

  /** При необходимости монтирует блоки и восстанавливает выделение. */
  restoreDOMSelection(
    selection: Selection,
    options?: RestoreDOMSelectionOptions,
  ): boolean;

  /** Фокусирует блок и устанавливает каретку, не меняя модель выделения. */
  focusBlock(
    position: EditorPosition,
    options?: RestoreDOMSelectionOptions,
  ): boolean;

  /** Фокусирует поверхность без изменения позиции прокрутки. */
  focus(): boolean;

  /** Перемещает каретку по визуальным строкам. */
  verticalCaretPosition(
    position: EditorPosition,
    direction: "up" | "down",
  ): EditorPosition | undefined;

  /** Возвращает геометрию для существующего алгоритма вставки. */
  collectDropLayout(): readonly DropLayoutBlock[];
}

```

Реализации:


| Реализация               | Ответственность                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `PageSurfaceAdapter`     | Поиск блоков страницы, виртуализация, порядок выделения, работа с кареткой и измерение геометрии для перетаскивания. |
| `EdgelessSurfaceAdapter` | Поиск и измерение блоков на холсте; передача текстовых операций адаптеру соответствующей карточки.                   |


Обе реализации используют общие DOM-функции выделения. Алгоритмы обхода текстовых узлов и восстановления диапазонов не должны дублироваться.

Важно различать отсутствующий блок и существующий, но несмонтированный блок. Во втором случае адаптер страницы сначала монтирует его. Если блок удалён, операция возвращает неуспех.

**2. Расширение существующего менеджера поверхностей**

Сейчас `SurfaceManager` регистрирует React-компоненты, обёртки и слоты. Его следует расширить регистрацией адаптеров смонтированных поверхностей:

```
interface SurfacesCapability {
  // Существующие методы регистрации сохраняются.

  registerAdapter(
    root: HTMLElement,
    adapter: SurfaceAdapter,
  ): () => void;

  /** Находит адаптер поверхности, содержащей браузерный узел. */
  resolveAdapter(node: Node): SurfaceAdapter | undefined;

  /** Находит поверхность блока в текущем React-редакторе. */
  resolveBlockAdapter(blockId: string): SurfaceAdapter | undefined;
}

```

Эти методы реализует `SurfaceManager`.

Регистрация выполняется на границе React, где уже существует ссылка на корневой DOM-элемент. Возвращаемая функция удаляет конкретную регистрацию при размонтировании. Для вложенной карточки должен находиться её адаптер, а не адаптер окружающего холста.

После этого код выделения и навигации перестаёт самостоятельно искать `PageVirtualizationController`. Адаптер страницы обращается к существующему контроллеру внутри своей реализации.

**3. Расширение существующего менеджера выделения**

`ReactSelectionManager` остаётся публичным владельцем координации выделения. Добавляем операции фокуса:

```
interface SelectionCapability {
  // Существующие методы выделения и планирования сохраняются.

  /** Устанавливает модель каретки и восстанавливает фокус после рендера. */
  focusCaret(
    position: EditorPosition,
    options?: RestoreDOMSelectionOptions,
  ): () => void;

  /** Планирует фокус для уже установленной модели каретки. */
  scheduleBlockFocus(
    position: EditorPosition,
    options?: RestoreDOMSelectionOptions,
  ): () => void;
}

```

`ReactSelectionManager` реализует эти методы через соответствующий адаптер поверхности и существующий `scheduleIfSelectionUnchanged`.

Разница между операциями:

- `focusCaret` сразу меняет модель выделения.
- `scheduleBlockFocus` сохраняет модель и планирует браузерный фокус.
- Обе возвращают функцию отмены.
- Новое выделение, замена поверхности или документа, уничтожение редактора отменяют устаревшую работу.

Вызов:

```
focusCaret(reactEditor, root, blockId, offset);

```

заменяется на:

```
reactEditor.selection.focusCaret({ blockId, offset });

```

Под этими операциями нужно объединить дублирующееся преобразование текстового смещения в DOM-позицию из packages/react-rivto-editor/src/managers/events/block-dom.ts:170 и packages/react-rivto-editor/src/managers/selection/editor-dom-selection.ts:519.

Нативные `Node` остаются внутри браузерного кода выделения. Через границу адаптера проходит `EditorPosition`.

**4. Контекст поверхности в событиях редактора**

`EventManager` уже определяет ID блока один раз для каждого события. Аналогично он должен определять адаптер поверхности:

```
interface EditorEventInit {
  // Существующий контекст события сохраняется.

  readonly surface: SurfaceAdapter;
}

```

`EditorEvent` получает это свойство, а `EventManager` заполняет его.

Обработчик навигации выглядит так:

```
const next = event.surface.verticalCaretPosition(position, "down");

if (next) {
  event.reactEditor.selection.focusCaret(next);
}

```

Обработчик больше не ищет элементы и не монтирует виртуализированные соседние блоки.

Нативное событие остаётся доступным: нужны модификаторы клавиатуры, информация о вводе и управление стандартным поведением браузера. Поля с DOM-элементами могут оставаться для браузерных расширений, но обычная логика использует нормализованный контекст.

После переноса потребителей можно убрать `root` из `BlockViewContext`, если он нужен им только для фокуса и выделения.

**5. Отдельный контроллер перетаскивания**

PageDragProvider (packages/react-rivto-editor/src/extensions/block-drag/provider.tsx:108) должен рендерить провайдер и превью, а также преобразовывать события dnd-kit. Состоянием активного перетаскивания управляет конкретный класс `PageDragController`.

Его контракт:

```
interface DragController {
  /** Фиксирует перемещаемые блоки и исходное выделение. */
  start(blockId: string): boolean;

  /** Рассчитывает позицию вставки и обновляет обратную связь. */
  update(
    point: PointerCoordinates,
    target: CrossDocumentPageRootController | null,
    options: DropLayoutOptions,
  ): void;

  /** Повторно проверяет назначение, выполняет перенос и завершает жест. */
  commit(): boolean;

  /** Завершает жест без изменения документа. */
  cancel(): void;

  /** Отменяет активную работу и освобождает ресурсы. */
  destroy(): void;
}

```

`PageDragController` реализует этот контракт и остаётся внутренней частью расширения перетаскивания. Глобальный менеджер перетаскивания не нужен.

Контроллер отвечает за:

- Зафиксированный набор перемещаемых блоков и исходное выделение.
- Текущее назначение в своём или другом документе.
- Обновление хранилища позиции вставки.
- Проверку перед переносом и восстановление выделения.
- Повторно безопасное завершение жеста.

Интеграция с dnd-kit отвечает за сенсоры, прямоугольник клавиатурного перетаскивания и преобразование событий библиотеки. Превью остаётся в React. Отслеживание указателя остаётся браузерной операцией.

**6. Убираем корневой DOM-элемент из междокументного перетаскивания**

Существующий контракт можно изменить так:

```
interface CrossDocumentPageRootController {
  readonly reactEditor: ReactEditor;
  readonly surface: SurfaceAdapter;

  resolvePlacement(
    point: PointerCoordinates,
    sources: readonly EditorBlock[],
    options: DropLayoutOptions,
  ): {
    readonly destination: BlockDropDestination;
    readonly indicator: DropPlacement | null;
  } | null;

  setPlacement(
    placement: DropPlacement | null,
    empty?: boolean,
  ): void;
}

```

Браузерный код по-прежнему находит поверхность назначения через DOM. После поиска контроллер перетаскивания работает с этим контрактом.

Для пустого документа должно существовать явное назначение `BlockDropDestination`, даже если нет блока, к которому можно привязать индикатор.

Перенос выполняется через существующие менеджеры блоков и функции междокументного переноса. Перед завершением повторно проверяются структура назначения и допустимость вставки: документ мог измениться во время жеста.

**Что сохраняется**

Существующие `resolveDropPlacement`, типы назначения, модель выделения, расчёты привязки и менеджеры мутаций ядра остаются основой. Для преобразования координат сначала нужно переиспользовать `canvasPoint`; отдельный менеджер для этого не требуется.

Измерения DOM должны учитывать прокрутку, изменение размеров и масштабирование. Само появление адаптера не является причиной вводить постоянный кеш геометрии.

Классы здесь нужны для владения состоянием и временем жизни. Чистые вычисления остаются функциями.

**Порядок реализации и критерии готовности**

1. Объединить преобразование текстовых позиций; добавить операции фокуса в `ReactSelectionManager`.
2. Ввести адаптеры поверхностей и их регистрацию; перенести выделение и навигацию.
3. Добавить адаптер поверхности в события; убрать повторное определение DOM-контекста.
4. Выделить `PageDragController`; перенести междокументное назначение.

Работа завершена, когда обычной логике взаимодействий больше не нужны корневые DOM-элементы, а браузерная интеграция сохраняет доступ к ним.

Проверки должны покрывать направление выделения, виртуализированную навигацию, вложенные карточки, отмену перетаскивания, управление с клавиатуры, перенос между документами, редактор внутри iframe и очистку ресурсов при размонтировании или замене документа. После реализации обязательна проверка производительности по правилам репозитория.
