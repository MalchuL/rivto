# Markdown editing and preview geometry

`MarkdownContent` uses two representations of the same persisted block
content:

- `.markdown-editor` is the raw `contenteditable` Markdown source.
- `.markdown-preview` is the presentation generated by `react-markdown`.

The raw editor remains mounted so browser ranges and collaborative source
offsets stay stable. While idle, it is an absolutely positioned transparent
interaction layer and therefore does not contribute to layout. The formatted
preview supplies the idle block geometry. Raw source overflow is clipped in
this state so extra Markdown delimiters and code-fence lines cannot extend the
invisible interaction layer over following blocks.

When the raw editor receives focus, React removes the preview and returns the
editor to normal layout flow. Blurring mounts the updated preview again. Thus
only the visible representation participates in block height:

```text
idle:    formatted preview controls height; editor is an absolute click layer
editing: raw editor controls height; formatted preview is not mounted
```

The clipping is removed as soon as editing begins. The raw editor may then grow
naturally to fit its complete source; it is never given a fixed height or an
internal scrollbar.

Typing updates the block through the following path:

1. The raw `contenteditable` emits an `input` event.
2. `useBlockEditing()` persists plain-text content through the editor.
3. The editor revision rerenders `MarkdownContent`.
4. The raw editor grows only according to source wrapping and line breaks.
5. After blur, `react-markdown` mounts a preview from the latest source.

Markdown remains presentation only. Parsing does not create blocks or modify
the document hierarchy.

## Extending the preview

An editor extension can register remark plugins, rehype plugins, and React
renderer composition through `editor.markdown.register`. Registrations belong
to the installing extension and mounted previews update when they are added or
removed. Plugins execute synchronously, in registration order, after the
built-in GFM and code processing for their respective stages. Renderer
contributions receive the renderers installed before them and the source block
ID and bounded block operations. Wrap the previous renderer to preserve its
behavior for nodes your extension does not claim.

```tsx
const example = {
  id: "example.markdown",
  setup(editor) {
    editor.markdown.register({
      components: (components) => ({
        ...components,
        // Add or wrap a renderer here.
      }),
    });
  },
};
```

A contribution may set `plainTextSafe: true` only when none of its plugins or
renderers can affect a single-line source containing letters, numbers, spaces,
and hyphens. Otherwise leave it unset: such text must go through the Markdown
pipeline for the contribution to run. The demo's `linkPreviewExtension`
shows a link renderer that delegates other links to the previous renderer.

The optional file and image extensions register their own Markdown macro
parsers, renderers, and inline attachment formatters. Removing one extension
removes its contributions; an image-specific formatter is available only while
the image extension is installed. Raw HTML remains disabled and the normal URL
transform still applies. Plugins and custom renderers are host-provided code
and must uphold the application's content and URL policy.

## Automatic link titles

`markdownLinkTitleExtension({ resolveTitle })` adds website titles and favicons.
When a Markdown block loses focus, the extension finds bare HTTP URLs and asks
`resolveTitle(url, signal)` for each title. Successful results replace the URLs
with Markdown links. Existing links, code, image URLs, and macro contents are
left alone. If a lookup fails or the block changes while a lookup is pending,
the original content is retained. Removing the extension aborts pending lookups.

The resolver belongs to the host because browsers restrict cross-origin page
requests. The demo uses the public Microlink API: each URL requiring a title is
sent to that service. Hosts can provide their own resolver and data policy.
Favicons are requested from each link's origin. Plain-text image URLs without a
recognized image filename extension are treated as ordinary links; copied HTML
image elements continue to use image handling.

## Fenced code

Fences accept either a language name or a file path:

````markdown
```bash
echo "Rivto"
```

```src/example.js
const value = 42;
```
````

`bash` is displayed as the code label and selects Bash highlighting.
`src/example.js` remains visible as the filename while `.js` selects JavaScript
highlighting. Common JavaScript, TypeScript, Python, shell, web, systems, data,
and markup extensions are inferred. Unknown extensions remain renderable and
may use automatic language detection.

Highlighting is provided by `rehype-highlight`. It transforms ReactMarkdown's
syntax tree into escaped React elements; user-authored raw HTML remains disabled.
Theme colors are exposed through the `--rivto-code-*` CSS variables.

## Constraining editor height

Applications can constrain unusually long source text with a theme override:

```css
.markdown-editor {
  max-height: 12rem;
  overflow: auto;
}
```

These are theme-level choices; no editor or block implementation changes are
required.
